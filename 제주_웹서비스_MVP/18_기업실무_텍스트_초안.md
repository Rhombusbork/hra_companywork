[ Ⅰ. 고객 문제 정의 ]

1. 과제가 요구한 것

과제는 제주 지역의 관광, 로컬 상품, 음식, 체험, 이동, 생활정보와 관련된 고객 불편을 하나 골라 간단한 웹서비스 MVP 로 푸는 것이다. 과제 안내에서 문제와 관련된 줄만 다시 읽으면 이렇다.

- 학습 목표 첫 줄: 고객 문제를 정의하는 방법을 익힌다.
- 평가지표 첫 줄: 문제 정의의 명확성. 그 뒤로 MVP 기능의 적절성, 사용 편의성, 문제 해결 만족도, 재사용 의향.
- 주의 사항: 로그인·결제·데이터베이스 연동은 요구하지 않는다. 완성도 높은 개발보다 고객 문제를 해결하는 최소 기능에 집중한다.

학습 목표와 평가지표가 모두 문제 정의로 시작한다. 그래서 무엇을 만들지보다 무엇을 풀지를 먼저 정하기로 했다. 과제를 받은 11월 20일에 처음 던진 질문도 기능이 아니었다. "웹서비스를 통해 해결할 수 있는 좋은 문제에는 개념적으로 어떤 문제들이 있어? 경영적으로 웹서비스는 주로 어떤 문제 해결을 위해 활용되어?"

2. "좋은 문제"의 기준 세우기

1) 책에서 가져온 기준

| 책 | 가져온 생각 |
|---|---|
| 에릭 리스 『린 스타트업』 | 아무도 원하지 않는 것을 잘 만드는 것이 가장 큰 낭비다. 가치 가설은 문제 해결 만족도로, 재방문은 재사용 의향으로 잰다 |
| 애시 모리아 『Running Lean』 | 문제와 함께 기존 대안을 먼저 적는다. 대안이 아무것도 없으면 문제가 아닐 수도 있다 |
| 롭 피츠패트릭 『The Mom Test』 | 아이디어를 묻지 말고 과거에 실제로 한 일을 묻는다 |
| 크리스텐슨 『일의 언어』 | "어떤 상황에서, 무엇을 하려는데, 무엇이 막는가"가 한 문장으로 나와야 한다 |
| 도널드 밀러 『무기가 되는 스토리』 | 문제는 외적·내적·철학적 세 겹이다 |
| 사보이아 『아이디어 불패의 법칙』 | 가설을 "적어도 X%의 Y가 Z할 것이다"로 쓴다. 피드백 정량화와 이어진다 |
| 폴 그레이엄 「How to Get Startup Ideas」 | 만드는 사람이 직접 겪는 문제, 소수가 깊이 원하는 문제가 좋다 |
| 피터 틸 『제로 투 원』 | 작은 시장을 완전히 잡는다. 타깃을 좁게 |
| 『스프린트』, 닐슨 | 5명이면 사용성 문제의 약 85%가 드러난다. 과제의 5명 테스트와 맞는다 |
| 니르 이얄 『훅』 | 자주 겪는 문제여야 습관이 된다. 재사용 의향과 이어진다 |

2) 웹이 잘 푸는 문제와 못 푸는 문제

거래비용(코스), 정보재(샤피로·배리언), 롱테일(앤더슨), 플랫폼(파커 외)에 관한 책에서 웹서비스가 잘 푸는 문제의 유형을 뽑았다.

| 유형 | 고객이 겪는 불편 | 웹서비스가 하는 일 |
|---|---|---|
| 정보가 흩어져 있다 | 여러 사이트·SNS·카톡방을 돌아다녀야 한다 | 한곳에 모아 한 화면에 |
| 찾기·비교가 어렵다 | 선택지가 너무 많거나 기준이 없다 | 조건으로 걸러 주고 비교표 |
| 판단·계산이 귀찮다 | 매번 머리로 따져야 한다 | 입력하면 계산·추천 결과 |
| 정보가 비대칭이다 | 파는 쪽은 알고 사는 쪽은 모른다 | 기준·가격·후기를 드러냄 |
| 타이밍·상태를 모른다 | 지금 열었는지, 언제까지인지 모른다 | 현재 상태를 보여 줌 |
| 절차가 복잡하다 | 서류·단계가 많아 포기한다 | 단계를 줄이고 대신 채워 줌 |
| 언어·접근 장벽 | 외국인·고령자는 못 쓴다 | 번역·쉬운 화면 |
| 수요와 공급이 못 만난다 | 서로 있는 줄 모른다 | 매칭 |

웹으로 풀기 어려운 문제도 함께 정리했다.

- 물리적인 문제: 길이 막힌다, 짐이 무겁다. 웹은 정보를 옮길 뿐 물건을 옮기지 못한다.
- 사람이 많이 모여야 가치가 생기는 문제: 후기, 중고 거래, 매칭. 5명 테스트로는 가치가 보이지 않는다.
- 규제·권한이 필요한 문제: 바가지요금이나 택시처럼 단속으로 풀 문제, 예약 확정처럼 권한이 있어야 하는 일.

로그인·결제·DB 가 없다는 과제 조건은 오히려 범위를 정해 주었다. 사용자끼리 주고받는 서비스, 내 기록이 쌓여야 하는 서비스는 맞지 않는다. 입력하면 결과 화면 한 번으로 끝나는 것이 맞는다. 계산기, 추천기, 체크리스트, 비교표, 조건 필터, 정보 모음 페이지 같은 것이다.

3) 기업은 웹서비스로 무엇을 푸는가

기업에게 웹서비스는 결국 더 벌거나 덜 쓰는 문제다. 마이클 포터는 「Strategy and the Internet」(2001)에서 인터넷을 그 자체로 전략이 아니라 가치사슬의 모든 단계에 붙는 도구로 보았다.

| 경영 문제 | 웹서비스가 하는 일 | 무엇으로 재나 |
|---|---|---|
| 고객이 우리를 모른다 | 검색·SNS에서 찾게 하고 첫 방문을 문의로 바꿈 | 방문자 수, 전환율 |
| 팔 곳이 좁다 | 매장·시간·지역 한계 없이 판매 | 매출 |
| 같은 질문에 사람이 계속 답한다 | 고객이 스스로 찾고 조회하게 (셀프서비스) | 상담 건수, 처리 시간 |
| 고객이 한 번 오고 안 온다 | 다시 올 이유를 만듦 | 재방문율 |
| 내부 일이 수작업이다 | 엑셀·전화·종이를 화면 하나로 | 처리 시간, 오류율 |
| 고객을 모른다 | 무엇을 보고 어디서 떠나는지 기록 | 의사결정에 쓰인 지표 |
| 새 사업 모델이 필요하다 | 중개·구독·플랫폼 | 거래액, 활성 사용자 |

여기에 『린 스타트업』의 관점을 하나 더한다. 웹서비스는 제품을 다 만들기 전에 수요를 확인하는 아이디어 검증 도구이기도 하다. 이번 MVP 가 그 용도다.

4) 한 줄 정의

위 내용을 한 장으로 줄였다.

- 특정한 사람이 자주 겪고, 지금은 불편한 방법으로 버티고 있으며, 정보를 입력하면 결과 화면 하나로 풀리는 문제.

| 조건 | 뜻 |
|---|---|
| 누가 겪는지 분명하다 | "관광객"이 아니라 "비 오는 날의 뚜벅이 여행객"처럼 좁게 |
| 실제로 겪었다 | 의견이 아니라 과거에 일어난 일로 확인된다 |
| 기존 대안이 있다 | 검색 여러 번, 카톡으로 묻기, 헛걸음 |
| 자주 겪는다 | 1년에 한 번 겪는 문제는 다시 쓰지 않는다 |
| 정보 문제다 | 흩어짐, 고르기 어려움, 지금 상태를 모름 |
| 입력 → 결과로 끝난다 | 로그인·결제·DB 없이 기능 2~3개로 풀린다 |

문장 틀도 정했다. [누가]는 [어떤 상황]에서 [무엇을 하려는데], [무엇] 때문에 막힌다. 그래서 [어떤 기분]이 든다.

3. 관광에서 제주대 정보로 좁힌 과정

1) 처음 후보는 관광이었다

과제 개요의 첫 단어가 관광이라 자연스럽게 관광부터 보았다. 출발점은 아는 형의 한마디였다. "제주의 문화 관광지가 정리된 프로그램이 없다." 이것이 진짜 문제인지 확인하는 방법을 먼저 정리했다.

- 책상에서: 블로그·지도 리뷰에서 후회·불편 문장 30개를 모아 유형별로 세기, 관광불편신고 집계(공공데이터포털), 국민신문고, 제주 방문관광객 실태조사.
- 발로: 공항 관광안내소·제주관광정보센터에 전화, 박물관 매표소·문화관광해설사, 게스트하우스 사장님.
- 묻는 법: 내 아이디어는 말하지 않고 "가장 자주 묻는 질문", "최근 기억나는 손님 이야기", "지금은 무엇을 보여 주며 안내하는지".
- 판단: 블로그 / 민원·조사 / 안내하는 사람 / 기존 대안 / 테스트할 5명 / 입력 → 결과 중 세 가지 이상 맞으면 고른다.

형의 말부터 따져 보니 걸리는 데가 있었다. 비짓제주·플레이제주 같은 서비스가 이미 있었다. 형이 겪은 문제가 정보가 "없다"인지, 많은데 "못 고른다"인지, 휴관·운영시간이 "틀렸다"인지부터 가려야 했다.

2) 제주대 정보로 바꿨다

다음 날인 11월 21일에 방향을 바꿨다. 그때 한 말은 이렇다.

"내가 다니는 제주대학교 관련 장학금, 행사 등의 정보를 모아 한번에 보여주는 웹사이트를 서비스하고 싶어. 특히 그 사람이 원하는 것이 정해져 있을 때 미리 말해 놓으면 그것과 관련된 것들만 계속 모으고 보여준다던지, 필요한 거 여러 사이트에 나누어져 있는 정보들을 한번에 모아 보여준다던지 하는 서비스."

바꾼 이유는 이렇다. 제주대 학생으로서 정보를 찾다 보면 학교 안 프로그램이나 그 밖에 신청할 수 있는 프로그램을 찾기 어려웠다. 그래서 평소에 이런 사이트가 있었으면 좋겠다고 생각했다. 반면 관광은 인스타그램, 여러 사이트, 렌터카 업체까지 여러 곳에서 홍보하고 있어서 관광 분야의 편의는 이미 충분하다고 보았다.

과제 개요의 "생활정보"에 제주대 학생의 생활정보로 들어간다고 보았다. 앞의 기준에 두 후보를 대 보면 차이가 분명했다.

| 기준 | 관광 | 제주대 정보 |
|---|---|---|
| 누가 겪는지 | 관광객, 좁혀도 문화시설 찾는 여행객 | 제주대 학생. 좁히면 장학금을 찾는 학생 |
| 실제로 겪었나 | 형 한 명의 말, 확인 전 | 직접 다니는 학교에서 겪음 |
| 기존 대안 | 비짓제주, 검색, 지도 | 학교·학과 게시판을 따로 들어가 보기, 단톡방 공지 |
| 얼마나 자주 | 여행할 때만, 1년에 몇 번 | 학기마다, 매주 |
| 정보 문제인가 | 못 고른다 / 틀렸다 중 무엇인지 모름 | 흩어짐 + 놓침 |
| 입력 → 결과 | 조건 → 추천 | 관심사 → 모은 글 |
| 5명 테스트 | 여행 온 사람을 찾아야 함 | 약학과·HRA 동기 |

4. 정말 흩어져 있는지 조사

1) 조사 방법

"정보가 흩어져 있다"가 이 문제의 핵심이다. 그래서 정말 그런지부터 셌다. 부탁한 범위는 넓었다. "제주대학교 관련 정보를 모을 수 있는 사이트들을 모두 찾고, 거기서 정보들을 끌어올 수 있을지(권한적으로 접근 및 정보 추출 및 실시간 업데이트가 바로바로 가능한지 등등) 정리해 줘. 다양한 과 홈페이지에만 올라오는 공지도 모아줄 수 있으면 좋을 것 같고."

AI 에이전트 다섯이 각기 다른 방법으로 찾았다. 본부 사이트, 학과 홈페이지, 학식·생활 정보, 학교 밖 정보원, 도메인 탐색이다. 그 결과를 하나로 합친 뒤 핵심 주소 21개는 직접 받아 확인했다. 11월 22일에는 학과 홈페이지 101곳을 하나씩 열어 공지 게시판 주소를 표로 만들었다.

2) 확인한 사실

- 공지가 올라오는 곳: 본부 공지, 학과 게시판(공지 주소가 있는 곳 92곳), 학생생활관, 진로취업센터, 국제교류본부, 제대로 산학1번지, 중앙도서관. 학교 밖까지 보면 45곳이다.
- 본부 공지는 2주에 76건이 올라왔다. 그중 장학은 4건이었다.
- 장학 공고의 마감일은 목록에 칸이 없다. 제목이나 첨부 안에만 있다. 마감일이 칸으로 있는 곳은 제대로 산학1번지 하나다. 국가장학금 1차 신청 안내는 본문이 jpg 한 장이었다.

6. 문제 정의와 타깃 사용자

1) 문제 정의

앞의 문장 틀에 넣으면 이렇다.

제주대 학생은 장학금·행사·학과 공지를 챙기려는데, 공지가 본부·학과·생활관·진로취업센터·국제교류본부에 흩어져 있고 마감일이 제목이나 첨부 안에만 있어서 놓친다. 그래서 놓쳤을까 봐 불안하고, 알고 보니 마감이 지나 있어 허탈하다.

『무기가 되는 스토리』의 세 겹으로 나누면 이렇다.

- 외적: 공지가 여러 곳에 흩어져 있고 마감일이 첨부 안에 있다.
- 내적: 놓쳤을까 봐 불안하다. 알고 보니 마감이 지나 있어 허탈하다.
- 철학적: 받을 수 있었던 장학금을 몰라서 못 받는 일은 없어야 한다.

2) 타깃 사용자와 기존 대안

- 주 타깃: 제주대 학부생
- 보조 타깃: 대학원생, 기숙사생, 복수전공·교직 이수 학생

지금 학생들이 버티는 방법은 학교·학과 게시판을 하나씩 들어가 보는 것, 학과 단톡방 공지, 그리고 에브리타임에 묻는 것이다. 그래서 우리의 진짜 경쟁자는 다른 앱이 아니라 "그냥 단톡방에 물어보기"다. 그보다 빨라야 쓴다. 학생들이 가장 많이 여는 에브리타임과의 비교는 Ⅱ-7 에 정리했다.

3) 왜 웹서비스로 풀기 좋은 문제인가

| 기준 | 이 문제 |
|---|---|
| 정보 문제다 | 정보가 흩어져 있고, 마감(타이밍)을 모른다 |
| 물리·규제 문제가 아니다 | 공지는 이미 로그인 없이 공개돼 있다. 모아서 거르기만 하면 된다 |
| 사람이 모여야 가치가 생기지 않는다 | 첫 사용자 한 명도 바로 쓸모를 본다. 후기·매칭이 아니다 |
| 입력 → 결과로 끝난다 | 학과·관심사를 넣으면 모은 글이 마감 순으로 나온다 |
| 로그인·결제·DB 없이 된다 | 설정은 브라우저에, 글은 하루 몇 번 파일로 |
| 기능 2~3개로 풀린다 | 모아 보기 / 마감 표시 / 내 학과 |
| 자주 겪는다 | 장학 공지는 주 3~5건, 학식은 매일 |
| 5명을 찾을 수 있다 | 약학과·HRA 동기 |

경영의 말로 바꾸면 학생 쪽에서는 탐색비용을 줄이고, 학교 쪽에서는 같은 질문에 답하는 응대 비용을 줄이는 셀프서비스에 가깝다. 에브리타임에 같은 질문을 올리고 다른 학생이 답해 주는 일이 지금 그 비용을 대신 치르고 있다.

- 장학의 자리: 필수로 두지 않고 선택 항목 맨 위에 둔다.

2) 학년은 뺐다 (11/25)

학년을 받으면 학년에 맞는 글을 고를 수 있다. 미국 대학생 취업 플랫폼 Handshake 도 학년을 묻는다. 그런데 Handshake 는 학교 학적 자료를 밤마다 받아 와서 값이 저절로 맞는다. 우리는 로그인이 없어서 3월이 되면 저장된 학년이 틀린다. 그래서 학년은 빼고, 필요하면 "졸업 준비" 같은 항목을 직접 고르게 했다. 학년이 정말 필요 없었는지는 테스트에서 묻는다.

3) 분류는 적게, 칩으로 거른다 (11/25)

처음에는 분류 카드가 많았다. 졸업요건·자격, 학사·수업·등록, 산학 프로그램, 행사·봉사, 취업·인턴이 모두 따로였다. 서로 겹쳐서 줄였다.

- 학사·수업·등록은 "학사" 하나로 묶고 수업·등록·학적·학사일정 칩으로 나눈다.
- 산학 프로그램과 행사·봉사는 "프로그램·행사" 하나로 묶는다.
- 취업·인턴은 교외 채용 글이 많아 따로 두고 인턴·채용·진로 프로그램 칩을 붙인다.

원칙은 하나다. 큰 카드는 적게 두고, 카드 안에서 칩으로 유형을 거른다. 마지막에 누른 칩은 기억한다.

4) 상세 창과 북마크 (11/25~26)

처음 판은 제목을 누르면 학교 원문이 새 탭으로 바로 열렸다. 휴대폰에서는 학교 사이트로 튀어 나간 뒤 돌아오기가 번거롭다. 그래서 두 번째 시안을 따로 만들었다. 제목을 누르면 우리 쪽 상세 창이 먼저 뜨고, 거기서 게시일, 마감과 그 출처, 첨부 이름을 본 뒤 북마크하거나 원문을 연다. 11월 26일에 두 시안을 하나로 합쳐 한 주소에 두었다.

5) 첫 화면: 바로 홈으로, 그리고 다시 설정으로 (11/26~27)

11월 26일에 첫 화면을 뒤집었다. 그때 한 말은 이렇다. "학과 선택부터 있으면 귀찮아서, 건너뛰기 하고 나오는 게 기본 옵션이고 학과를 원하면 넣을 수 있게 하는 게 더 좋을 거 같아." 그래서 처음 들어오면 아무것도 묻지 않고 바로 홈이 뜨게 했다. 학과는 홈 위의 "학과 넣기" 한 줄에서 원하는 사람만 넣는다.

11월 27일 화면을 다시 짜면서 처음 설정 세 단계(나 → 볼 것 → 홈 화면)를 다시 넣었다. 대신 두 가지는 남겼다. "건너뛰고 둘러보기"를 누르면 바로 홈으로 가고, 한 번 저장한 사람은 다시 와도 바로 홈이다. 학과 주소(`?dept=약학과`)로 들어온 사람에게는 아무것도 묻지 않는다. 학과 단톡방에 이 주소를 올리면 받은 사람은 고르지 않아도 자기 학과로 들어온다.

볼 것을 고르는 화면은 맥킨지 뉴스레터를 고르는 화면처럼 카드로 만들었다. 카드마다 ✓/+ 버튼, 얼마나 자주 올라오는지, 미리보기가 있다.

어느 쪽이 맞는지는 테스트에서 확인한다. 학과를 넣었는지, 안 넣었다면 왜 안 넣었는지를 묻는다.

3. 핵심 기능

1) 한곳에 모아 보기

여러 게시판의 글을 분류 칸으로 모은다. 칸은 학사, 장학, 생활관, 프로그램·행사, 취업·인턴, 국제교류, 제주 청년이다. 학과가 본부 글을 다시 올린 것은 하나로 합치고 "OO에도 게시"라고 붙인다. 앞 칸에 나온 글은 뒤 칸에서 빼서 같은 글을 두 번 보지 않게 했다.

2) 마감 표시

마감이 남은 글은 마감이 가까운 순으로, D-day 와 함께 보인다. 마감일 옆에는 그 날짜를 어디서 읽었는지 붙인다. 게시판의 마감 칸에서 읽었는지, 제목의 "(~12/4)" 같은 표기에서 읽었는지다. 틀린 마감일은 없는 것보다 해롭기 때문이다. 홈에는 "가장 먼저 마감", "그다음 마감", "이번 주 마감 수" 칸이 있다.

3) 내 학과

원하는 사람만 학과를 넣는다. 넣으면 학과 게시판 글, 학과가 다시 올린 본부 글, 졸업요건·자격 글이 맨 위 칸에 뜬다. 칩으로 졸업·학사, 졸업요건·자격, 근로·학과장학, 교직, 취업·채용, 실습·특강, 행사를 거른다. 학과를 고르면 학부/대학원과 캠퍼스가 자동으로 채워지고, 계열에 맞는 분류가 추천된다.

그 밖의 기능은 이렇다.

- 오늘 학식: 백두관, 6호관, 1호관, 사라캠퍼스. 자주 가는 식당을 고르면 그 식당만 보이고, 지금 시간에 맞는 끼니가 먼저 열린다(10시 전 아침, 15시 전 점심, 그 뒤 저녁).
- 오늘·달력: 오늘 일정과 이달 달력을 한 칸에. 일정 탭 달력에는 마감·학사일정·북마크를 찍는다.
- 북마크: 제목 옆 ☆. 북마크 창에서 휴대폰 캘린더 파일(.ics)로 내보낸다.
- 제목 검색, 키워드 모아 보기·숨기기, 정보원 숨기기.
- 구독: 마감·학사일정 캘린더 구독(.ics), 분류·학과별 RSS.
- 휴대폰 홈 화면에 앱처럼 추가.
- 설정 코드로 다른 기기에 설정 옮기기.

4. 사용자 입력 항목

모두 선택이다. 아무것도 넣지 않아도 쓸 수 있다.

| 입력 | 메모 |

| 주전공 | 넣으면 학부/대학원·캠퍼스가 자동으로 채워지고 계열에 맞는 분류를 추천 |

7. 에브리타임과 비교

제주대 학생이 가장 많이 여는 학교 앱은 에브리타임일 것이다. 에브리타임에도 학교 공지로 가는 길이 있으니, 우리 서비스가 따로 필요한지 따져 보았다.

| | 에브리타임 | 제주대 모아보기 |
|---|---|---|
| 주된 내용 | 학생 게시판(취업·진로, 홍보, 동아리), HOT 글, 채팅 | 본부·학과·센터 공지, 장학, 학사일정, 학식 |
| 학교 공지 | "학사공지·학사일정·도서관" 같은 바로가기 아이콘 (학교 페이지로 넘어가는 것으로 보임) | 여러 게시판 글을 직접 모아서 한 목록으로 보여 줌 |
| 개인화 | 즐겨찾는 게시판, 시간표 | 학과를 고르면 그 학과 게시판 글이 맨 위로, 관심 분류·키워드 |
| 마감 | 따로 정리하지 않음 | 제목·게시판 칸에서 마감일을 읽어 D-day, 달력, 북마크 |
| 학식 | 한 곳의 한 끼 (확인한 화면에서는 6호관 저녁) | 자주 가는 식당 + 시간에 맞는 끼니 탭, 1호관 인스타 메뉴까지 |
| 홈 꾸미기 | 정해진 배치 | 칸을 옮기고·키우고·숨기기 |
| 가입 | 학교 인증 로그인 필요 | 로그인 없음, 광고 없음 |
| 알림 | 앱 푸시 알림 | 없음 (화면 표시와 캘린더 구독으로 대신) |

출처: 에브리타임 앱 화면 (2026-11-27 확인)

1) 우리 서비스만 하는 것

- 흩어진 공지를 한곳에: 학교 공지는 본부, 학과, 국제교류, 진로취업, 생활관, 도서관, 제주청년센터 게시판에 흩어져 있다. 에브리타임은 이 게시판들로 가는 길만 열어 주고, 우리 서비스는 글 자체를 모아서 내 학과 기준으로 걸러 준다.
- 마감 정리: "이번 주에 마감되는 게 뭐지?"에 바로 답한다. D-day 표시, 달력, 휴대폰 캘린더 구독(.ics)이 있다.
- 학과 게시판 모으기: 학과 홈페이지 공지는 에브리타임에 바로가기도 없다. 다만 지금은 약학·간호 두 학과만 모으고 있다.

2) 에브리타임이 더 나은 것

- 알림: 에브리타임은 앱이라 새 글을 푸시로 알려 준다. 우리 서비스는 서버가 없어서 들어와야 보인다.
- 실시간성: 에브리타임 글은 올라오는 즉시 보인다. 우리 서비스는 하루 4번 모으는 방식이라 몇 시간 늦을 수 있다.
- 사람과 생활 기능: 학생들의 후기, 질문, 정보 공유와 시간표·채팅·중고거래는 우리 서비스에 없다.

3) 두 서비스의 관계

에브리타임이 "학생들의 이야기"라면, 모아보기는 "학교가 나에게 해야 할 말"을 마감 순으로 정리해 준다. 두 서비스는 경쟁이라기보다 서로 비어 있는 곳을 채워 주는 관계에 가깝다. 실제로 이 서비스를 만든 이유 가운데 하나가 에브리타임에 올라온 "어디서 보나요" 글들이었다(Ⅰ-5).

8. 데이터를 다루는 규칙

- 분류: 본부 공지에는 학교가 붙인 분류 번호가 있다(학사 320, 수업 321, 등록 322, 장학 323, 행사 200, 봉사 197). 이 번호를 먼저 따르고, 번호가 없으면 제목 키워드로 나눈다.
- 정렬: 마감이 남은 글은 마감이 가까운 순, 나머지는 게시일 최신 순.
- 중복: 학과가 본부 글을 다시 올리면 글 번호가 새로 붙는다. 제목으로 묶어 본부 글 하나로 보여 준다.
- 새 글: 처음 본 시각을 기준으로 하되 게시일 이틀 뒤까지만 새 글로 친다.
- 저장하는 것: 제목, 날짜, 작성 부서, 첨부 이름, 원문 링크. 본문과 작성자 칸은 저장하지 않는다.

공지는 모두 200건이다. 다른 학과를 고르면 "이 학과 게시판은 아직 모으지 않아요"와 그 게시판 링크를 보여 준다.

2. 바이브코딩으로 일한 방식

1) 말로 정하고 AI 가 만든다

코드는 거의 다 Claude Code 에게 말로 시켜 만들었다. 수집기(파이썬), 화면(처음엔 HTML·자바스크립트, 11월 27일부터 React), 자동 수집(GitHub Actions), 화면을 눌러 보는 시험까지 모두 그렇다. 사람이 한 일은 무엇을 만들지, 무엇을 뺄지 정하고, 화면을 직접 눌러 보고 고칠 점을 말하는 것이었다.

AI 에게 일을 맡기면서 지킨 규칙이 몇 가지 있다.

- 정한 것은 문서로 남긴다. 00 과제 정리부터 18 이 텍스트까지 번호를 붙인 문서가 19개다. 큰 결정은 06 이어하기에 날짜와 함께 한 줄씩 남겼다.
- 조사 문서에는 직접 확인한 것 [확인] 과 짐작 [추측] 을 나눠 적는다.
- 사용자 말을 거의 그대로 문서에 넣고, AI 가 예시나 계획을 마음대로 덧붙이지 않는다. 덧붙일 것은 [제안] 으로만.
- 저장소가 공개라서 실명·연락처·학번·카톡 캡처·API 키는 올리지 않는다.

2) 여러 사람, 여러 세션

조원이 번갈아 작업했다. 집 PC 의 Claude Code 와 브라우저에서 쓰는 웹 Claude Code 를 오갔고, 11월 23일에 다른 조원도 함께 작업할 수 있게 이 과제만 새 저장소로 옮겼다. 그날 인수인계 문서(README)를 만들었다.

- 갈라지지 않게 작업이 끝날 때마다 커밋하고 바로 main 에 올린다. 시작할 때는 먼저 받아 온다.
- 웹 Claude Code 의 기본 환경은 학교 도메인을 막는다. 학교 도메인을 허용한 환경을 따로 만들어야 했다.

저장소의 커밋은 11월 27일까지 72개다. 사람과 AI 가 한 커밋이 63개, 자동 수집 봇의 커밋이 9개다.

3) 밤사이 스스로 고치는 루프 (11/26 밤)

11월 26일 밤에는 잠든 사이에 AI 가 사이트를 계속 고치게 했다. 그때 한 부탁은 이렇다. "계속 개선할 요소를 찾고 이에 대해 인터넷을 최대한 많이 검색하고 그걸 바탕으로 개선하는 거야. 꼭 사이트의 기능적인 측면보다도, 우리가 이걸로 더 많은 문제를 해결할 수는 없는지, 더 나은 해결책은 없는지, 연관되어 있지만 더 강한 경제적 효과를 가져올 문제 및 해결이 없는지 같은 것도 찾아보고 싶어."

규칙과 할 일 목록을 문서(16)로 먼저 정하고, AI 가 한 바퀴마다 목록에서 하나를 골라 고친 뒤 작업 기록(17)에 한두 줄을 남기게 했다.

- 문제 방향은 바꾸지 않는다. 더 좋은 문제를 찾아도 제안 문서로만 쓴다.
- 외부 서비스 가입, API 키, 돈이 드는 일은 하지 않는다.
- 학교 사이트에는 정해진 수집 말고 추가로 요청하지 않는다.
- 끊겨도 괜찮게: 작업은 따로 떼어 둔 브랜치에서 하고, 화면 시험을 통과한 것만 main 에 합친다. 큰 일은 작게 쪼개 단계마다 커밋한다.
- 재량으로 정한 것은 [재량], 사람이 봐야 할 것은 [확인 필요] 로 표시한다.

밤 10시 40분부터 새벽 1시 10분까지 돌았고, 한 일은 이렇다. 두 시안 합치기, 화면을 눌러 보는 시험 41개, 학사일정 실제 수집, 새 글 표시 고침, 분류 고침, 중복 정리, 안 모으는 학과 안내, 달력 고침, 제주청년센터 추가, 수집 실패 시 자동 알림, 제목 검색, 홈 화면에 추가, 캘린더 구독·RSS, 문서 정리, 제출용 캡처, 학교 협조 메일 초안. 인터넷 조사(사이트 설계 연구, 비슷한 서비스, 더 풀 수 있는 문제, 경제 효과)는 차례가 오기 전에 멈췄다.

5. 부딪힌 문제와 대응

1) 학교 사이트가 자동 수집을 막아 두었다

학교 본부 사이트들의 robots.txt 는 `Disallow: /`, 곧 전체 차단이다. 그래서 다음처럼 최소한으로만 읽기로 했다.

- 목록 첫 페이지만, 하루 2~4회, 요청 사이 2.5초.
- 요청에 서비스 이름과 저장소 주소를 밝힌다.
- 모든 글에 원문 링크를 달고, 본문·포스터는 옮기지 않는다.
- 한 바퀴에 학교 사이트 요청은 13번, 30초쯤 걸린다.

학교에 알리고 협조를 구하는 메일 초안도 써 두었다. 읽는 범위와 횟수, 저장하지 않는 것, 연락처, 그리고 RSS 나 공식 데이터가 있는지 묻는 내용이다. 보낼지는 아직 정하지 않았다.

2) 학교 서버의 인증서

학교 서버가 중간 인증서를 보내지 않아 보안 연결 검증이 실패했다. 검증을 끄면 쉽게 넘어가지만 그러지 않았다. 중간 인증서를 따로 받아 저장소에 넣고, 그것까지 합쳐 검증하게 했다.

3) 학교 쪽이 연결을 끊었다

11월 26일 밤, 루프가 고칠 때마다 자동 수집이 함께 돌아 몇 분 간격으로 요청이 몰렸다. 그 직후부터 학교 사이트들이 연결을 끊었다. 11월 27일 아침 정기 수집에서도 본부·생활관·국제교류·진로취업·학과 게시판·학교 식단표는 실패했다. 산학1번지·도서관·청년센터·1호관은 정상이었다.

- 실패한 곳은 이전 글을 그대로 보여 준다. 그래서 사이트가 비지는 않았다.
- 수집이 실패하면 저장소에 "자동 수집 실패" 이슈가 자동으로 열리고, 다시 성공하면 닫힌다. 이번에 처음으로 이 기능이 실제로 쓰였다.
- 코드를 고칠 때는 수집이 돌지 않게 바꿨다.

robots.txt 를 지키겠다고 정해 놓고도, 짧은 시간에 요청을 몰리게 한 것은 우리 실수였다.

(공란: 발표 전까지 연결이 풀렸는지, 학교 메일을 보냈는지)

4) 1호관 학식

1호관 점심·저녁 메뉴는 업체 인스타그램에만 올라온다. 인스타그램은 약관이 자동 수집을 막아서 직접 읽지 않기로 했다. 업체 홈페이지에 인스타 최근 게시물을 보여 주는 위젯이 있어 이것을 읽는 방법을 시험했다.

- 업체 홈페이지는 데이터센터 IP 를 막아서(403) 처음에는 GitHub Actions 에서 열리지 않을 것으로 보았다.
- 11월 27일 새벽 집 PC 에서 시험했을 때는 위젯의 글 칸 39개가 모두 비어 있었다. 그래서 링크만 두기로 했다.
- 같은 날 화면을 다시 짜면서 위젯의 글과 천원의 아침밥 게시판을 읽게 바꿨고, 지금은 1호관 메뉴가 들어온다.

시험할 때마다 결과가 달랐다. 남의 사이트 구조에 기대는 수집은 언제든 다시 멈출 수 있다.

5) 공개 저장소

과제 조건에 맞추려고 GitHub 무료 기능만 쓰다 보니 저장소가 공개다. 그래서 수집한 글도 공개된다. 작성자 칸과 본문은 저장하지 않고, 개인 이름이 든 제목이 없는지 본다. 에브리타임 캡처 같은 자료는 저장소에 올리지 않았다.

시간이 되면 T2 를 학교 사이트에서도 해 보게 하고 걸린 시간을 비교한다.

4) 폼 문항

그 밖에 단과대·학년·기숙사, 최근 한 학기 동안 공지를 놓친 적이 있는지, 공지를 주로 어디서 보는지, 가장 쓸모 있던 기능을 묻는다. 학과를 넣었는지와 안 넣은 이유, 학년이 필요했는지도 묻는다. 이 둘은 첫 화면과 학년에 대해 내린 결정(Ⅱ-2)을 확인하려는 것이다.

3. 개선 제안

테스트 전이라 순위는 비워 두었다. 테스트에서 많이 나온 문제부터 순위를 매긴다.

1) 이미 반영한 것

처음에 개선 제안으로 적었다가 만들면서 넣은 것들이다.

- 제목 검색
- 휴대폰 홈 화면에 추가
- 마감·학사일정 캘린더 구독(.ics): 서버 없이 휴대폰 캘린더가 마감 하루 전에 알려 준다.
- 분류·학과별 RSS 12개
- 제주청년센터 소식
- 수집이 실패하면 자동으로 이슈 열기
- 1호관 메뉴

2) 정보를 더 정확하게

① AI 첨부 읽기

장학·프로그램 공지는 마감일이 제목엔 없고 첨부(PDF·한글·이미지 한 장)에만 있는 경우가 많다. 지금 사이트는 제목과 게시판 칸에서만 마감일을 읽는다.

- 방법: 수집기가 새 글의 첨부 이름과 주소를 이미 저장하고 있다. 새 글 중 PDF·이미지 첨부가 있는 것만 하루 한 번 받아 AI 에 넘기고, 마감일과 세 줄 요약을 채운다. 화면에는 이미 "AI 추정" 표시 자리가 있다.
- 빼는 것: 제목에 결과·명단·합격·선발자가 들어간 글은 개인정보 때문에 읽지 않는다.
- 드는 것: AI API 키와 호출 비용.
- 위험: 잘못 읽은 마감일은 없는 것보다 해롭다. "AI 추정, 원문에서 꼭 확인" 표시를 지우지 않는다. 첨부는 읽고 버린다.
- 순서: 첨부를 받으면 학교 사이트 요청이 늘어난다. 학교 협조 메일을 먼저 보내는 것이 맞다.

② 날짜의 뜻까지 보여 주기

에브리타임의 수강포기 글처럼 날짜를 보고도 무엇의 마감인지 잘못 이해할 수 있다. 학사일정에 "신청 기간"과 "만료일"을 구분해 적는 것을 제안한다.

3) 정보를 더 넓게

- 학과 확대: 약학·간호 → 테스트한 학생들의 학과 → 전체. 104곳을 모두 받으면 한 번에 요청이 13번에서 약 115번으로 는다. 학과는 하루 2번으로 줄여 나눠 받는다.
- 학교와 공식 협조: 메일로 알리고 RSS·공식 데이터가 있는지 묻는다. 학교가 허락하거나 데이터를 주면 robots.txt 문제와 연결 끊김이 함께 풀린다.
- 학교 밖: 한국장학재단 자료, 청년정책 API. 공공데이터포털 키가 필요하고 승인에 시간이 걸린다.

4) 쓰기 편하게

- "덜 보기": 글마다 "이런 글 덜 보기"(SmartNews).
- 학기 초 다시 묻기: 3월·9월에 "이번 학기에도 이대로 볼까요?"(Handshake).
- 방문 수 세기: 쿠키 없는 통계로 재사용 의향을 숫자로 본다. 외부 서비스 가입이 필요하다.
